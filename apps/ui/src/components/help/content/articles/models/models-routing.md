The session model runs the manager. A worker uses the manager's own model unless the manager names a worker preset, which sets that worker's model and reasoning level.

## Manager model

The manager model owns task framing, execution, coordination, and acceptance. Pick a model capable of doing the project's work directly. You can set a project default, override one session, or return a session to the project default.

For a local Builder project, use **Project Settings → Default model → Change** to set the project default and supported reasoning level. The existing project-header **Change Default Model** shortcut remains available. Override a single session with **Override Session Model**, or use **Use Project Default** to copy the current project default onto that session without future tracking. In eligible Builder manager sessions, the compact model pill beside **Send** shows the effective model and reasoning level and opens a compact nested menu for either choice. Choosing **Use Project Default** applies the current project default to that session. Changing the project default affects only new conversations; existing sessions keep their model. New Project/Create Project uses the same model-aware reasoning selector, with unsupported options hidden and defaults applied when reasoning is omitted.

## Worker models

The manager works directly and spawns workers when you ask or when a worker clearly helps: separable parallel work, a different model, or an independent check. A worker preset is a name, a model, a reasoning level, and an optional note. Manage the flat, global list under **Settings → Worker presets**. Specialist markdown files you wrote appear in the same list and carry their own worker instructions.

Native xAI routing also follows the effective credential. `grok-4.6` is the family default, `grok-4.5` remains an explicit variant, and both are available to normal manager create, change, and exact per-session override selectors when xAI auth is configured. Authenticated OAuth discovery can add `grok-build` and `grok-composer-2.5-fast` only for entitled accounts; these remain OAuth-only worker choices excluded from normal manager selectors. Switching to API-key auth hides the entitlement models and rejects stale selections before a provider request. Losing entitlement or failing discovery removes them from refreshed catalog, projection, and selector results. The xAI Composer ID is separate from Cursor SDK `composer-2.5`. xAI/Grok is not eligible for manager compaction.

### User-added OpenRouter manager models

OpenRouter rows follow a stricter exact-model path than Forge's built-in families. Forge derives `supportsTools` only from live OpenRouter metadata when adding a model and when OpenRouter Settings loads and reconciles stored exact IDs; request-body capability claims are ignored. Settings reconciliation automatically refreshes matched legacy rows. The backend must have live-verified `supportsTools: true`; unmatched or unrefreshable rows, an absent field, or `supportsTools: false` remain non-manager and fail closed until a later live verification. Reconciliation refreshes only `supportsTools`; it does not enable manager agents or mutate the exact row's default-off `managerEnabled` opt-in. Each verified row remains manager-disabled by default. Enable only that model's **Manager agents** setting with `managerEnabled: true` under `openrouter:<exact-model-id>`; the override does not create a family, preset, or alias. The same key can store an optional context cap from **Context window** **Apply**/**Reset**; manager-enabled and **Configure routing** stay independent of that cap.

A manager create, change, or session override must name `{ provider: "openrouter", modelId: "<exact-model-id>" }`, and an OpenRouter API key must be configured. Unknown, unverified, disabled, credential-less, or retired IDs fail closed rather than falling back to another provider. Removing a row deletes the whole override key, including any context cap; re-adding it starts with manager access off and no cap. Retired OpenRouter IDs remain rejected rather than migrated across providers. Worker use of a retained legacy row is a separate path and does not make it manager-eligible.

OpenRouter manager eligibility is also separate from compaction: OpenRouter remains outside the supported compaction provider list and its models are not compaction choices.

Each added OpenRouter card has a **Context window** token input with **Apply** and **Reset**. Enter a positive whole number of tokens; blank Apply or Reset removes only the cap. The effective maximum is the lower of the advertised window and the cap, so a cap cannot increase capacity. Advertised metadata and max-output capability stay unchanged while the runtime request budget uses the effective context. Caps persist under `openrouter:<model-id>` in `shared/config/model-overrides.json` and apply when an agent next starts; running agents keep their current snapshot.

OpenRouter provider routing is a separate control. Shared defaults and exact-model overrides in **Settings > Models** constrain which OpenRouter endpoints may serve the next call. Preferred provider order is not a hard allowlist; allowed/excluded lists, ZDR, denied collection, price ceilings, quantizations, required parameters, and disabled OpenRouter endpoint fallback are. OpenRouter endpoint fallback happens inside OpenRouter. Shared required ZDR and disallowed collection cannot be weakened per model. These filters apply only to OpenRouter inference routing, not local transcripts, tools, or non-OpenRouter summarization/compaction. Discovery metadata is advisory. See the Provider Guide for the full control list and OpenRouter's [provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) documentation.
