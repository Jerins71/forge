# Forge V2 (`feat/v2-core`)

This branch replaces Forge's orchestration core and reshapes the product around **environments**.
It is not merged to `main` yet. This page is the fastest way to run it and find your way around.

## Run it safely

**Never point a V2 build at the data directory of an installed Forge.** On first boot V2 rewrites
some stored state: rosters become worker presets, and legacy work-mode and roster fields are dropped
from session descriptors. Use a fresh directory, or a copy of your data if you want your projects.

Requirements: Node.js **26.5.0** (`.nvmrc`) and the pnpm version in `package.json`. Native
modules such as `better-sqlite3` are built for the Node that ran `pnpm install`; if you switch Node
versions, reinstall.

```bash
git checkout feat/v2-core
pnpm install --frozen-lockfile

# Backend + web UI with hot reload, on an isolated data directory
FORGE_DATA_DIR="$HOME/.forge-v2" pnpm dev
# Backend: http://127.0.0.1:47187   UI: http://127.0.0.1:47188
```

To try the desktop shell instead, run `FORGE_DATA_DIR="$HOME/.forge-v2" pnpm dev:electron`.
If an installed Forge Desktop is running, quit it first or use different ports (`FORGE_PORT`), and
keep the data directory separate either way.

Copying an existing data directory (`cp -R ~/.forge ~/.forge-v2`) is fine for trying V2 with real
projects. The copy is upgraded in place; the original is untouched.

Providers: sign in under **Settings → Authentication**. Claude and Codex run through their native
harnesses (the Claude Code CLI and the Codex app server). Each also supports an API key with a
custom Base URL for routers or proxies; Codex Base URLs normally end in `/v1`.

## Run a remote environment from source

On the remote machine (Linux or macOS), with the same Node and pnpm:

```bash
git checkout feat/v2-core && pnpm install --frozen-lockfile
for p in @forge/protocol @forge/client-runtime @forge/backend @forge/cli; do pnpm --filter $p build; done
node packages/cli/dist/cli.js serve \
  --backend-entry "$PWD/apps/backend/dist/index.js" \
  --data-dir "$HOME/.forge-v2" --port 47687 --pair \
  --tailscale-serve --public-url "https://<machine>.<tailnet>.ts.net"
```

`--pair` prints a one-time pairing link (valid for 60 seconds) when the backend is ready. Paste it
into **Settings → Environments → Add environment** on your machine. Remote access requires HTTPS.
`--tailscale-serve` publishes the loopback backend on the machine's Tailscale HTTPS name (port 443);
if that port is already served, publish it yourself or use `--public-url` with
`--tls-cert`/`--tls-key`. Run
`node packages/cli/dist/cli.js help serve` for every option. Keep the process running (tmux or a
user service); restart without `--pair` afterwards.

## What changed

- **Environments.** Every Forge backend is an *environment*: this machine, or another machine you
  pair. Settings → Environments lists them. A session runs on the environment you choose and never
  falls back to another one. The same Git repository on several machines shows as one project in the
  sidebar.
- **Remote machines.** For a Linux host you reach over SSH, **Settings → Environments → Add over
  SSH** installs Forge there as a user service and pairs it. To run a source checkout on another
  machine instead, see [Run a remote environment from source](#run-a-remote-environment-from-source).
- **Orchestration core.** Runs, attempts, provider bindings, choices, worker assignments and
  recovery are decided by a pure kernel and persisted in SQLite with an effect outbox
  (`apps/backend/src/environment/control/orchestration/`). Provider runtimes report facts; the
  kernel decides outcomes. Live events and replayed history project from the same records.
- **Worker presets replace work modes and rosters.** A manager works directly and starts a worker
  when parallel work, a different model or an independent check clearly helps. Presets are a flat
  list of name, model, reasoning and an optional note (Settings → Worker presets). Without a preset,
  a worker uses its manager's model; when you ask for a specific model ("start a Haiku worker"), the
  manager can name it exactly. Forge ships one preset, `plan-consultant`; upgrades drop the
  routes Forge shipped in its rosters. See [SPECIALISTS.md](SPECIALISTS.md).
- **No automatic project onboarding.** A new project starts idle; the first message is its first
  turn.
- **Conversation behaviour.** Live tool and reasoning activity, sending while a reply streams (the
  message is taken in mid-reply, or queued until the current step ends), Stop that keeps the text
  already shown, readable provider errors, and failed-turn alerts in Needs you.
- **Composer.** Native Claude and Codex sessions show the model and reasoning only. The
  context-management control applies to Pi-backed sessions. `/compact [instructions]` compacts the
  session like **Compact context** (Codex refuses instructions), and the header meter shows the
  provider's last reported context usage.

## Where things live

| Area | Path |
|---|---|
| Environment service, identity, pairing, exposure | `apps/backend/src/environment/` |
| Control plane: commands, effects, SQLite, migrations | `apps/backend/src/environment/control/` |
| Orchestration kernel and its tests | `apps/backend/src/environment/control/orchestration/` |
| Provider runtimes (Claude, Codex, Pi, Cursor) and replay fixtures | `apps/backend/src/swarm/runtime/` |
| Worker presets | `apps/backend/src/swarm/specialists/worker-presets.ts` |
| Environment wire contract | `packages/protocol/src/environment-v2.ts` |
| Client runtime used by the UI and CLI | `packages/client-runtime/` |
| Multi-environment E2E harness | `scripts/environment-e2e/` |

## Testing

- **Unit and replay tests:** run the explicit Vitest files for what you changed (see `AGENTS.md`).
  Provider behaviour is pinned by replay tests built from real provider traffic: fixtures under
  `apps/backend/src/swarm/runtime/{claude,pi}/replay/` and the Codex replay tests in
  `apps/backend/src/swarm/__tests__/`.
- **E2E fleets:** `scripts/environment-e2e/*.spec.ts` launch real backends (a local machine plus
  paired remotes) with a scripted Codex provider (`fake-codex.mjs`). Build the UI with the test
  platform first, or UI specs wait forever on "Waiting for connection":

  ```bash
  VITE_FORGE_E2E_PLATFORM=1 pnpm --filter @forge/ui build
  pnpm exec playwright test scripts/environment-e2e/ux.spec.ts --config scripts/environment-e2e/playwright.config.ts
  ```

  `pnpm quality:full` rebuilds the UI without that flag, so rebuild before running UI specs after it.
- **Full pre-merge check:** `pnpm quality:full`, then the E2E specs `ui`, `ux`, `slice`, `cli`,
  `lineage-ui`, `activity` and `polish`.
- **Real providers:** the fleets never need real keys. When you do test against real providers, use
  an isolated data directory and never commit or print credentials.

## Known gaps

- Pairing a headless machine requires restarting it with `--pair`, and the link expires after 60
  seconds.
- A paired environment whose credential is lost disappears from the list instead of asking to
  re-pair.
